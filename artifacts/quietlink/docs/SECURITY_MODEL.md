# Hidden Messenger security model

## Current build status

The app does not send messages or media, make real calls, publish statuses, receive remote push alerts, or transfer data to another device. Text sending and media sharing remain locked because no reviewed E2EE protocol or encrypted transport is installed. `security/secureMessaging.ts` defines fail-closed text and media-key adapter boundaries; it does not implement a messaging protocol. The app configures a native libsodium binding for X25519-backed `crypto_box` and XChaCha20-Poly1305 primitives. These primitives are not a reviewed messaging protocol and are not wired into message or transfer flows. The API includes a short-lived WebSocket signaling gateway, but the mobile app does not connect to it yet. In Expo Go, web, or any binary without SQLCipher, the secure vault and local media import fail closed. A rebuilt native iOS/Android binary configured with SQLCipher stores conversation data and local media-key metadata in the encrypted vault.

The chat provider opens the vault before showing screens. The adapter checks for SQLCipher and fails closed rather than using plaintext SQLite. The secure-message boundary will only pass protocol-produced ciphertext envelopes to a configured transport. No protocol engine or transport is installed, so sends remain disabled. On native builds with the encrypted vault, users can import photos, videos, and audio for local storage only. Media is never sent, and no E2EE key wrapper is installed.

## Voice, calls, sounds, notifications, and permissions

1. On a rebuilt native iOS/Android binary with SQLCipher, Expo Audio's in-memory PCM stream feeds the voice-note writer; the app never calls Expo Audio's file-recording API. Each PCM chunk is AES-256-GCM encrypted with a fresh nonce and context-bound AAD before its frame is written to the app-owned `.hmvn` file. The per-note key and SQLCipher metadata are kept in the encrypted vault. Playback reads, authenticates, and passes one bounded chunk at a time to a native in-memory renderer (AVAudioEngine on iOS, AudioTrack on Android); temporary JS/native buffers are cleared best-effort. The voice-note screen is local-only; no message send or key-wrap path exists while E2EE remains unselected. Web, Expo Go, and builds missing either native module or encrypted storage keep record/play controls disabled.
2. The call route contains incoming, outgoing, and active-layout previews for voice and video. They are explicitly labeled previews. Accepting the incoming preview may request microphone/camera permission, but no call is connected, no camera feed is opened, and no audio/video is transmitted. The existing WebSocket signaling gateway is not wired to the mobile client and cannot by itself provide media transport or E2EE.
3. Short bundled PCM tones are used only for in-app ringtone/ringback/disconnect and chat-sound previews. Call tone and vibration preferences are saved with SecureStore. No contact names, message text, media, or keys are included in notification payloads.
4. `expo-notifications` is configured with a generic foreground handler, an Android notification channel, response routing, and local generic alert scheduling. Local notifications can be tested on a native build after permission is granted. Remote push is not operational: there is no push-token registration endpoint, Expo/APNs/FCM sender, or incoming message/call event feed. Do not claim that minimized apps can receive real calls or messages yet.
5. Runtime settings request camera access through Expo Image Picker, microphone access through Expo Audio, photo-library access through Expo Image Picker, and notification access through Expo Notifications. Requests are user-initiated; denied permissions offer a device-settings fallback. A permission grant does not imply that the corresponding call, voice recording, or push service is implemented.
6. App preferences are kept in Keychain/Keystore-backed SecureStore. Message and media records remain in SQLCipher; notification copy stays generic regardless of the preview preference UI.

## Phone OTP authentication

1. The native iOS/Android app accepts a Bangladesh subscriber number and sends it to the API. The API normalizes it to `8801XXXXXXXXX`, generates a cryptographically random six-digit code, and sends it to `https://api.sms.net.bd/sendsms` with an HTTPS JSON POST. The `SMS_NET_BD_API_KEY` exists only in API-server Secrets; it is never included in the mobile bundle.
2. The API stores only an HMAC-SHA-256 digest of the pending code, keyed with `SESSION_SECRET`, in process memory. Codes expire after five minutes, are single-use, and allow at most five attempts. Requests are limited to one per phone per minute, three per phone per fifteen minutes, and ten per client IP per fifteen minutes. Neither codes nor phone numbers are written to application logs.
3. Successful verification creates a random 256-bit opaque bearer token. The server stores only its SHA-256 digest in memory for up to thirty days. The mobile app stores the token and account phone in iOS Keychain / Android Keystore-backed SecureStore; the iOS token is device-only. Sign-out requests revocation and removes local values even if the API is unreachable.
4. OTP challenges, rate-limit counters, and sessions are intentionally process-memory-only in this prototype. A server restart invalidates active sessions and pending codes; multiple API replicas do not share them. A production deployment needs a shared store with atomic expiration and rate limiting, plus operational abuse monitoring, without persisting OTP plaintext.
5. The SMS provider receives the destination phone number and the verification message, and telecom operators may retain SMS metadata/content. Phone OTP proves access to a phone number; it is not end-to-end encryption, does not hide phone identity from the SMS provider, and does not authenticate the existing signaling gateway. The current API has no account directory, protected chat API, or authenticated WebSocket signaling.
6. The login flow is disabled in web preview because the web platform cannot provide the app's native secure token storage. A native iOS/Android build and a configured `SMS_NET_BD_API_KEY` are required for a real SMS login.

## Target architecture

```text
Mobile client A  <---- end-to-end encrypted payloads ---->  Mobile client B
       |                                                     |
       +--------- ephemeral WebSocket signaling ------------+
                              |
                       Signaling service
```

1. Use an established, independently reviewed end-to-end protocol implementation. Do not invent key exchange, ratchets, message authentication, or group cryptography. Device keys should be generated locally and kept in platform-protected key storage.
2. The API WebSocket route at `/api/signal` creates a random, short-lived pairing room and accepts only WebRTC offers, answers, and ICE candidates. The room/token state exists in process memory for up to two minutes; the gateway has no database or persistent queue. Do not accept message bodies or media on signaling routes. The service can still observe connection metadata and signaling SDP/candidates, including IP addresses and timing. A process restart destroys all active pairings.
3. WebRTC data channels can carry peer-to-peer payloads when network conditions allow. Some users will need a TURN relay because NAT/firewalls prevent direct paths. A TURN relay can see traffic metadata and must relay only already-encrypted payloads; this is not a guarantee of a direct connection or zero server exposure.
4. Use an encrypted SQLCipher database for message records in a rebuilt iOS/Android binary. SQLCipher's native configuration is enabled for both platforms; the SQLCipher v4 default page cipher is AES-256-CBC with an HMAC. Obtain a random 256-bit database key using a cryptographically secure random source and store it in Keychain/Android Keystore-backed storage. Never hard-code or log it. `secureChatDb.ts` checks for SQLCipher support before opening, sets the key before reading schema data, and the chat provider uses it for text and conversation metadata only when cipher support is confirmed.
5. `security/cryptoPrimitives.ts` wraps libsodium's native X25519-backed `crypto_box` and XChaCha20-Poly1305 primitives. The native binding is a third-party bridge with a subset of libsodium's API; this app and bridge have not received an independent security audit. Use per-purpose keys and authenticated context. These primitives do not provide identity verification, a ratchet, replay protection, or an E2EE session protocol; do not use them alone for chat or migration.
6. Encrypt media before writing it to the app sandbox. The current local-only path uses Expo Crypto's native AES-GCM module (CryptoKit on iOS and the platform JCA provider on Android) with a fresh random 256-bit key per file, a fresh 96-bit nonce per 64 KiB chunk, a 128-bit tag, and AAD binding the chunk to the conversation, attachment, type, and position. The file key is stored only in the SQLCipher-protected metadata table. A bounded streaming decrypt API authenticates each chunk before passing it to a caller; the chunk, ciphertext frame, and partial read buffers are cleared after use or on errors. JavaScript/native runtime copies and key objects are not guaranteed to be physically zeroized.
7. The document picker is called with `copyToCacheDirectory: false`. The selected source remains in its original Photos/files provider and is not modified or deleted by Hidden Messenger. If the native file handle cannot read the granted URI directly, import fails; there is no plaintext cache-copy fallback. App-owned media output is ciphertext only. The chat UI does not load arbitrary image URIs; until a native renderer exists, it shows a locked placeholder instead of a thumbnail. No preview file or media content is written to logs.
8. A new-device transfer should require explicit approval on both devices, establish an authenticated encrypted session using a reviewed protocol, stream the vault over the local link, verify integrity, and only then offer the user a choice to remove the old copy. A QR code should carry only a short-lived pairing secret or public key—not chat data or a reusable account secret.

## Deletion limits

The app must not claim forensic-proof deletion. Flash storage controllers, filesystem snapshots, app backups, operating-system caches, and journal behavior can leave data outside an app's control. Overwriting a file is not a reliable way to erase flash storage. A product can delete records and media, remove temporary data it owns, and destroy the vault key as best-effort cryptographic erasure. The UI must describe those limits and treat backup/export copies separately.

The delete action removes message/conversation rows from SQLCipher when the native encrypted vault is active, or removes them from memory in preview mode. The settings screen offers an explicit vault reset that deletes the database and current key, then creates a new empty vault. Media keys are inside SQLCipher; losing the vault key makes remaining media ciphertext unreadable. This is best-effort cryptographic erasure, not a secure wipe; the app cannot run cleanup code when uninstalled.

## Native build steps for the encrypted vault

1. Keep `expo-sqlite` configured with `useSQLCipher: true` and build a new native iOS/Android binary. A JavaScript reload or Expo Go session cannot enable SQLCipher.
2. Store a random 32-byte database key in platform secure storage. Expo SecureStore maps to iOS Keychain and Android Keystore-backed storage; the iOS item is restricted to the current device and Android SecureStore preferences are excluded from automatic backup. Do not derive it from a user PIN without a reviewed KDF and a recovery plan.
3. Open the database, verify `PRAGMA cipher_version` is present, set `PRAGMA key` immediately, and perform a read before migrations. Refuse to continue if the cipher check or read fails.
4. Apply schema migrations transactionally. Use parameterized statements for user-controlled values; only the validated local hexadecimal key is interpolated in the SQLCipher PRAGMA.
5. Verify fresh install, app restart, wrong-key handling, reset, device restore, and deletion behavior on physical Android and iOS devices. Verify that the document picker does not create an app-cache copy with `copyToCacheDirectory: false`; the import must fail rather than fall back to plaintext copying. OS backups may include the encrypted media container and SQLCipher database, but the app must never put plaintext media or file keys into those app-owned files.
6. The current local media flow stores ciphertext only. The voice-note path streams authenticated PCM chunks to native in-memory audio output and does not create a plaintext audio file or thumbnail. Unit tests cover interrupted reads/writes, invalid GCM tags, and buffer cleanup, but do not compile or execute the native Swift/Kotlin modules. Before shipping, build and test the custom iOS/Android binaries on devices; review OS audio behavior, backups, crash reporting, notifications, screenshots/app-switcher previews, memory lifetime, and logs. Do not make forensic-proof deletion claims.
7. The native libsodium plugin requires a rebuilt custom iOS/Android binary; Expo Go does not contain this native module. Validate compilation and crypto smoke tests on physical iOS and Android devices.
8. Build a custom iOS/Android binary after adding Expo Audio and Notifications, then validate permission prompts and local alerts on physical devices. Web preview cannot verify native permission behavior, call audio, or background delivery.
9. Complete a third-party security review and publish a threat model before making production privacy or security claims.

## Native media privacy audit status

The source review confirms that app-owned image/video/audio imports are written as authenticated ciphertext containers (`.qlm`), with file keys stored in SQLCipher metadata. The picker requests `copyToCacheDirectory: false`, and an unreadable provider URI fails instead of copying plaintext into cache. The chat screen does not render decrypted photos or videos; it shows a locked placeholder. Voice notes are stored as authenticated ciphertext frames and rendered as PCM through native in-memory audio output. The media and voice-note storage modules do not log media bytes, file keys, or picker URIs, and this project has no configured third-party crash-reporting integration.

The app does not currently configure screenshot/app-switcher protection. Media contents are not rendered in the chat preview, but ordinary chat text and contact names can appear in an OS snapshot. The app also does not exclude its encrypted media containers or SQLCipher database from operating-system backups. If backed up, those app-owned files contain ciphertext; the vault key is stored with device-only iOS Keychain accessibility, and Android SecureStore backup exclusion is configured. Generated native backup rules, restore behavior, OS crash diagnostics, and actual app-switcher snapshots have not been inspected on devices.

This is a source-level review only, not a device privacy certification. Importing provider files, interrupted reads, corrupted-tag rejection, file cleanup, backup contents, and snapshot behavior still require testing in rebuilt custom iOS and Android binaries. This workspace has no Xcode, Java/Android SDK, or physical test devices, so those checks are not claimed as passing.

## Known non-goals in this prototype

- No WhatsApp branding, copied assets, or exact proprietary screen reproduction.
- Phone OTP is a limited prototype identity check only; there is no account directory, phone discovery, key verification, Signal Protocol implementation, TURN server, WebRTC data channel, protected chat API, or message delivery. The ephemeral signaling gateway exists but the mobile client does not use it and does not authenticate its WebSocket connections. Real voice/video calls and remote push are not implemented.
- No E2EE media-key wrapping or media sharing; the protocol-matched wrapper interface fails closed until the user selects a reviewed E2EE protocol. Local file keys are only protected by SQLCipher at rest.
- No decrypted photo/video renderer; those media types remain locked. The voice-note renderer handles authenticated PCM only and still needs native build/device verification.
- Voice-note recording and playback are implemented as a local-only native path in source, but require a rebuilt binary containing the local renderer module and SQLCipher. Native compilation and physical-device behavior have not yet been verified. Voice notes are not transmitted or E2EE-wrapped.
- No secure overwrite or anti-forensics feature.
- No app-managed cloud backup. Operating-system backup behavior still needs platform-specific review. The prototype does not yet have a P2P migration implementation.
