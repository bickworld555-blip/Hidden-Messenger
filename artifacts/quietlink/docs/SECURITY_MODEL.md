# Hidden Messenger security model

## Current build status

Text sending, media sharing, publishing statuses, and device transfer are not enabled. Generic push-token registration and a privacy-limited sender are implemented, but this prototype has no account-bound incoming message or call event feed. One-to-one WebRTC audio/video calling is implemented in the native client source: it uses the API's ephemeral signaling gateway, a one-time QR pairing token, a second QR check of both DTLS fingerprints, and WebRTC DTLS-SRTP media encryption. Media capture is withheld until the joining device scans the matching fingerprint QR. The calls feature is not yet compiled or verified on physical iOS/Android devices; web preview and Expo Go fail closed if native WebRTC is unavailable. `security/secureMessaging.ts` still defines fail-closed text and media-key adapter boundaries; it does not implement a messaging protocol. The native libsodium binding provides X25519-backed `crypto_box` and XChaCha20-Poly1305 primitives, but these are not a reviewed messaging protocol and are not wired into chat or transfer flows. In Expo Go, web, or any binary without SQLCipher, the secure vault and local media import fail closed. A rebuilt native binary configured with SQLCipher stores conversation data and local media-key metadata in the encrypted vault.

The chat provider opens the vault before showing screens. The adapter checks for SQLCipher and fails closed rather than using plaintext SQLite. The secure-message boundary will only pass protocol-produced ciphertext envelopes to a configured transport. No messaging protocol engine is installed, so text sends remain disabled. On native builds with the encrypted vault, users can import photos, videos, and audio for local storage only. Media is never sent, and no E2EE key wrapper is installed.

## Voice, calls, sounds, notifications, and permissions

1. On a rebuilt native iOS/Android binary with SQLCipher, Expo Audio's in-memory PCM stream feeds the voice-note writer; the app never calls Expo Audio's file-recording API. Each PCM chunk is AES-256-GCM encrypted with a fresh nonce and context-bound AAD before its frame is written to the app-owned `.hmvn` file. The per-note key and SQLCipher metadata are kept in the encrypted vault. Playback reads, authenticates, and passes one bounded chunk at a time to a native in-memory renderer (AVAudioEngine on iOS, AudioTrack on Android); temporary JS/native buffers are cleared best-effort. App backgrounding, opening the in-app call route, OS audio interruption/focus loss, audio-route changes, and media-service reset stop capture or playback. Capture drains pending writes and aborts the writer instead of inserting a SQLCipher row; playback is cancelled and native pending PCM buffers are zeroed. The UI offers a retry state. At startup, cleanup opens and validates SQLCipher, reads the note IDs, and only then lists direct files in the dedicated voice-note directory. It best-effort removes unmatched UUID-named `.hmvn` ciphertext files, preserves row-backed and active files, and ignores other names. This is ordinary file deletion, not flash-level secure overwrite. The voice-note screen is local-only; no message send or key-wrap path exists while E2EE remains unselected. Web, Expo Go, and builds missing either native module or encrypted storage keep record/play controls disabled.
2. Native call sessions use `react-native-webrtc`; the module is dynamically loaded so web preview and Expo Go do not crash when its native code is absent. The caller creates a one-time pairing room and displays a QR containing the room ID, 256-bit join token, mode, and short expiry. The joiner scans it and explicitly accepts. The initial SDP negotiates a verification-only data channel; no audio/video track is created yet. Both clients derive the same 256-bit comparison value from the room/token and the caller/responder SHA-256 DTLS certificate fingerprints. The caller displays a second QR; the joiner must scan an exact match. Only then does the caller request media and offer audio/video; the joiner requests media only after receiving that verified media offer. Any mismatch, unavailable module, permission failure, or signaling error closes the session without a plaintext fallback.
3. WebRTC media uses DTLS-SRTP encryption between peers; the fingerprint QR provides an out-of-band check against SDP fingerprint substitution. It verifies the current connection, not a person's account, phone number, or long-term identity. The temporary invitation is a bearer token: share it only with the intended device and scan it promptly. There is no directory or account-authenticated signaling. The app does not send chat messages, voice notes, or file attachments over the call data channel.
4. The mobile call client connects to `wss://<EXPO_PUBLIC_DOMAIN>/api/signal`. The gateway relays only offers, answers, and ICE candidates, holds pairing state in memory, and never carries audio/video frames. Pairing tokens expire after two minutes; a joined call remains in memory for up to four hours or until either peer disconnects. SDP, candidate addresses, connection timing, and IP metadata are visible to the signaling and STUN services. The default STUN endpoint is configurable through `EXPO_PUBLIC_STUN_URL`; this prototype has no TURN service, so restrictive NAT/firewalls can prevent calls.
5. Short bundled PCM tones are used for outgoing ringback, disconnect, and chat-sound previews. Calls still start from a scanned invitation, not an account directory or background event feed; the current call flow therefore does not generate incoming-call pushes. Call tone and vibration preferences are saved with SecureStore.
6. `expo-notifications` supports local generic alerts, native push-token registration, generic foreground presentation, an Android notification channel, and notification-tap routing. Push registrations are persisted in shared PostgreSQL so an API restart does not require a backgrounded app to register again. The registry stores only an HMAC-derived opaque account ID, an HMAC token fingerprint, an AES-256-GCM-encrypted Expo token, and its expiry; it stores no phone numbers, message content, media, contact names, or notification history. The authenticated self-test cooldown is a separate row containing only the same opaque account ID and its expiration time, and its atomic claim works across API instances. Encryption and fingerprint subkeys are domain-separated with HKDF from `SESSION_SECRET`, which must remain stable across API restarts to restore registrations. Raw token values are decrypted only in memory for provider sends and are never logged. Expired, revoked, and provider-rejected device registrations are deleted. The API offers an authenticated generic self-test and an internal sender for future call/message event producers. Expo project ID and platform push credentials are required for delivery; set `EXPO_PUBLIC_EAS_PROJECT_ID` for builds that do not provide an EAS project ID. If Expo Push Security is enabled, configure `EXPO_ACCESS_TOKEN` in server Secrets. Remote push requires a rebuilt native app and does not work in the web preview or Expo Go on Android. The signaling and chat flows do not currently produce account-targeted events, so real incoming calls/messages cannot yet wake a minimized app.
7. Push payloads contain only generic copy (`Incoming call`, `New message`, or a generic test), an HMAC-derived opaque account ID, an opaque route ID, and an event type. They never contain message text, media, contact names, call bearer tokens, or encryption keys. Taps are held until authentication resolves and discarded if the account ID does not match the signed-in account. Message alerts open the chat list and call alerts open the calls screen; they do not bypass the current QR pairing/verification flow.
8. Runtime settings request camera access through Expo Image Picker, microphone access through Expo Audio, photo-library access through Expo Image Picker, and notification access through Expo Notifications. A call host requests microphone permission and video-camera permission before creating an invitation. A joiner also needs camera permission to scan the verification QR, including for audio-only calls. Media capture itself starts only after verification. Denied permissions offer a device-settings fallback.
9. App preferences and the current device's Expo push token are kept in Keychain/Keystore-backed SecureStore. The server persists only encrypted push-token registrations and their limited routing/expiry metadata; it does not persist messages, media, contact names, or notification history. Message and media records remain in SQLCipher; notification copy stays generic regardless of settings.
7. Runtime settings request camera access through Expo Image Picker, microphone access through Expo Audio, photo-library access through Expo Image Picker, and notification access through Expo Notifications. A call host requests microphone permission and video-camera permission before creating an invitation. A joiner also needs camera permission to scan the verification QR, including for audio-only calls. Media capture itself starts only after verification. Denied permissions offer a device-settings fallback.

## Phone OTP authentication

1. The native iOS/Android app accepts a Bangladesh subscriber number and sends it to the API. The API normalizes it to `8801XXXXXXXXX`, generates a cryptographically random six-digit code, and sends it to `https://api.sms.net.bd/sendsms` with an HTTPS JSON POST. The `SMS_NET_BD_API_KEY` exists only in API-server Secrets; it is never included in the mobile bundle.
2. The API stores only an HMAC-SHA-256 digest of the pending code, keyed with `SESSION_SECRET`, in process memory. Codes expire after five minutes, are single-use, and allow at most five attempts. Requests are limited to one per phone per minute, three per phone per fifteen minutes, and ten per client IP per fifteen minutes. Neither codes nor phone numbers are written to application logs.
3. Successful verification creates a random 256-bit opaque bearer token. The server stores only its SHA-256 digest in memory for up to thirty days. The mobile app stores the token and account phone in iOS Keychain / Android Keystore-backed SecureStore; the iOS token is device-only. Sign-out requests revocation and removes local values even if the API is unreachable.
4. OTP challenges, rate-limit counters, and sessions are intentionally process-memory-only in this prototype. A server restart invalidates active sessions and pending codes; multiple API replicas do not share them. A production deployment needs a shared store with atomic expiration and rate limiting, plus operational abuse monitoring, without persisting OTP plaintext.
5. The SMS provider receives the destination phone number and the verification message, and telecom operators may retain SMS metadata/content. Phone OTP proves access to a phone number; it is not end-to-end encryption, does not hide phone identity from the SMS provider, and does not authenticate the existing signaling gateway. The current API has no account directory, protected chat API, or authenticated WebSocket signaling.
6. The login flow is disabled in web preview because the web platform cannot provide the app's native secure token storage. A native iOS/Android build and a configured `SMS_NET_BD_API_KEY` are required for a real SMS login.

## Target architecture

```text
Mobile client A  <------- DTLS-SRTP media ------->  Mobile client B
       |                                               |
       +-- ephemeral WebSocket signaling (SDP/ICE) --+
                              |
                       Signaling service
```

1. Use an established, independently reviewed end-to-end protocol implementation. Do not invent key exchange, ratchets, message authentication, or group cryptography. Device keys should be generated locally and kept in platform-protected key storage.
2. The API WebSocket route at `/api/signal` accepts only WebRTC offers, answers, and ICE candidates. Unpaired room/token state is in memory for at most two minutes; a joined call expires after four hours, disconnect, or process restart. There is no database or persistent queue. The service can observe SDP/candidates, connection timing, and IP metadata, but it does not receive call media.
3. The call uses a data channel only for the short fingerprint-verification acknowledgement; chat text and attachments are rejected by the signaling gateway and are not sent over this channel. A default STUN service assists ICE discovery and sees network metadata. No TURN service is configured, so some NAT/firewall combinations will fail rather than fall back to a relay.
4. Use an encrypted SQLCipher database for message records in a rebuilt iOS/Android binary. SQLCipher's native configuration is enabled for both platforms; the SQLCipher v4 default page cipher is AES-256-CBC with an HMAC. Obtain a random 256-bit database key using a cryptographically secure random source and store it in Keychain/Android Keystore-backed storage. Never hard-code or log it. `secureChatDb.ts` checks for SQLCipher support before opening, sets the key before reading schema data, and the chat provider uses it for text and conversation metadata only when cipher support is confirmed.
5. `security/cryptoPrimitives.ts` wraps libsodium's native X25519-backed `crypto_box` and XChaCha20-Poly1305 primitives. The native binding is a third-party bridge with a subset of libsodium's API; this app and bridge have not received an independent security audit. Use per-purpose keys and authenticated context. These primitives do not provide identity verification, a ratchet, replay protection, or an E2EE messaging session protocol; do not use them alone for chat or migration.
6. Encrypt local attachments before writing them to the app sandbox. The current local-only path uses Expo Crypto's native AES-GCM module with a fresh random 256-bit key per file, a fresh 96-bit nonce per 64 KiB chunk, a 128-bit tag, and AAD binding each chunk to the conversation, attachment, type, and position. The file key is stored only in the SQLCipher-protected metadata table. A bounded streaming decrypt API authenticates each chunk before passing it to a caller; chunks and partial read buffers are cleared best-effort. JavaScript/native runtime copies and key objects are not guaranteed to be physically zeroized.
7. The document picker is called with `copyToCacheDirectory: false`. The selected source remains in its original provider and is not modified or deleted. If the native file handle cannot read the granted URI directly, import fails; there is no plaintext cache-copy fallback. App-owned media output is ciphertext only. The chat UI shows a locked placeholder instead of a decrypted attachment preview. No preview file or media content is written to logs.
8. A new-device transfer should require explicit approval on both devices, establish an authenticated encrypted session using a reviewed protocol, stream the vault over the local link, verify integrity, and only then offer removal of the old copy. A QR code should carry only a short-lived pairing secret or public key—not chat data or a reusable account secret.

## Deletion limits

The app must not claim forensic-proof deletion. Flash storage controllers, filesystem snapshots, app backups, operating-system caches, and journal behavior can leave data outside an app's control. Overwriting a file is not a reliable way to erase flash storage. A product can delete records and media, remove temporary data it owns, and destroy the vault key as best-effort cryptographic erasure. The UI must describe those limits and treat backup/export copies separately.

The delete action removes message/conversation rows from SQLCipher when the native encrypted vault is active, or removes them from memory in preview mode. The settings screen offers an explicit vault reset that deletes the database and current key, then creates a new empty vault. Media keys are inside SQLCipher; losing the vault key makes remaining media ciphertext unreadable. This is best-effort cryptographic erasure, not a secure wipe; the app cannot run cleanup code when uninstalled.

## Native build steps for the encrypted vault

1. Keep `expo-sqlite` configured with `useSQLCipher: true` and build a new native iOS/Android binary. A JavaScript reload or Expo Go session cannot enable SQLCipher.
2. Store a random 32-byte database key in platform secure storage. Expo SecureStore maps to iOS Keychain and Android Keystore-backed storage; the iOS item is restricted to the current device and Android SecureStore preferences are excluded from automatic backup. Do not derive it from a user PIN without a reviewed KDF and a recovery plan.
3. Open the database, verify `PRAGMA cipher_version` is present, set `PRAGMA key` immediately, and perform a read before migrations. Refuse to continue if the cipher check or read fails.
4. Apply schema migrations transactionally. Use parameterized statements for user-controlled values; only the validated local hexadecimal key is interpolated in the SQLCipher PRAGMA.
5. Verify fresh install, app restart, wrong-key handling, reset, device restore, and deletion behavior on physical Android and iOS devices. Verify that the document picker does not create an app-cache copy with `copyToCacheDirectory: false`; the import must fail rather than fall back to plaintext copying. OS backups may include the encrypted media container and SQLCipher database, but the app must never put plaintext media or file keys into those app-owned files.
6. The current local media flow stores ciphertext only. The voice-note path streams authenticated PCM chunks to native in-memory audio output and does not create a plaintext audio file or thumbnail. Unit tests cover interrupted reads/writes, interruption cleanup ordering, orphan-file reconciliation after SQLCipher opens, row/active-file preservation, invalid GCM tags, and buffer cleanup, but do not compile or execute the native Swift/Kotlin modules. Orphan cleanup uses ordinary file deletion and cannot guarantee physical flash blocks are overwritten. Before shipping, build and test the custom iOS/Android binaries on devices; review OS audio behavior, backups, crash reporting, notifications, screenshots/app-switcher previews, memory lifetime, and logs. Do not make forensic-proof deletion claims.
7. The native libsodium plugin requires a rebuilt custom iOS/Android binary; Expo Go does not contain this native module. Validate compilation and crypto smoke tests on physical iOS and Android devices.
8. Build a custom iOS/Android binary after adding Expo Audio, Camera, Notifications, SQLCipher, libsodium, and WebRTC. Validate permission prompts, audio routing, QR scanning, fingerprint mismatch rejection, call setup/teardown, and local alerts on physical devices. Web preview and Expo Go cannot verify native WebRTC behavior.
9. Complete a third-party security review and publish a threat model before making production privacy or security claims.

## Native media privacy audit status

The source review confirms that app-owned image/video/audio imports are written as authenticated ciphertext containers (`.qlm`), with file keys stored in SQLCipher metadata. The picker requests `copyToCacheDirectory: false`, and an unreadable provider URI fails instead of copying plaintext into cache. The chat screen does not render decrypted photos or videos; it shows a locked placeholder. Voice notes are stored as authenticated ciphertext frames and rendered as PCM through native in-memory audio output. The media and voice-note storage modules do not log media bytes, file keys, or picker URIs, and this project has no configured third-party crash-reporting integration.

The app does not currently configure screenshot/app-switcher protection. Media contents are not rendered in the chat preview, but ordinary chat text and contact names can appear in an OS snapshot. The app also does not exclude its encrypted media containers or SQLCipher database from operating-system backups. If backed up, those app-owned files contain ciphertext; the vault key is stored with device-only iOS Keychain accessibility, and Android SecureStore backup exclusion is configured. Generated native backup rules, restore behavior, OS crash diagnostics, and actual app-switcher snapshots have not been inspected on devices.

This is a source-level review only, not a device privacy certification. Importing provider files, interrupted reads, corrupted-tag rejection, file cleanup, backup contents, and snapshot behavior still require testing in rebuilt custom iOS and Android binaries. This workspace has no Xcode, Java/Android SDK, or physical test devices, so those checks are not claimed as passing.

## Known non-goals in this prototype

- No WhatsApp branding, copied assets, or exact proprietary screen reproduction.
- Phone OTP is a limited prototype identity check only; there is no account directory, phone discovery, Signal Protocol implementation, TURN server, protected chat API, or message delivery. The WebRTC client uses QR verification for each call, but the signaling connection is not authenticated to an account and QR pairing does not prove a contact's long-term identity. Native call compilation and device behavior are not yet verified.
- No E2EE media-key wrapping or media sharing; the protocol-matched wrapper interface fails closed until the user selects a reviewed E2EE protocol. Local file keys are only protected by SQLCipher at rest.
- No decrypted photo/video renderer; those media types remain locked. The voice-note renderer handles authenticated PCM only and still needs native build/device verification.
- Voice-note recording and playback are implemented as a local-only native path in source, including interruption-driven abort and retry handling, but require a rebuilt binary containing the local renderer module and SQLCipher. Native compilation and physical-device behavior have not yet been verified. Voice notes are not transmitted or E2EE-wrapped.
- WebRTC calls are source-implemented for native builds and require a rebuilt binary; the current development preview cannot verify native WebRTC, STUN reachability, audio routing, QR fingerprint verification, or native media teardown.
- No secure overwrite or anti-forensics feature.
- No app-managed cloud backup. Operating-system backup behavior still needs platform-specific review. The prototype does not yet have a P2P migration implementation.
